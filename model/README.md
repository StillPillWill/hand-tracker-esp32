# Soccer detector training

This folder defines a reproducible baseline training run. It does not claim that the model is ready for a full match: the source dataset contains broadcast-view frames, while the intended camera is a fixed iPhone on the sideline.

## Dataset

The baseline uses the [Football Image Dataset](https://github.com/skaczylo/Football-Image-Dataset), released under CC BY 4.0. It contains 612 1920×1080 frames: 512 train and 100 validation, with 500 labeled balls total (417 train, 83 validation), plus player and referee boxes. Credit the dataset author, skaczylo, and include the CC BY 4.0 license when redistributing adapted data or derived assets.

The dataset is downloaded and expanded under work/soccer-model, which is ignored by Git. It is not bundled in this repository. The upstream dataset's validation split is useful for checking that training runs, but it is too small and may not represent independent matches or the sideline viewpoint.

## Train a baseline

Python 3.10 or 3.11 and an NVIDIA GPU with CUDA are recommended. CPU training is supported but slow.

Run python -m pip install -r model/requirements.txt, then run python model/train_soccer.py from the repository root.

The script fine-tunes YOLO11n at 1280 pixels, evaluates the validation split, and exports a fixed-shape ONNX model. Outputs stay in work/soccer-model/training and are not committed automatically. Use `--name` to keep each experiment in its own run folder; `--weights` can point to a previous checkpoint. Use `--validate-only --weights path\to\best.pt --name experiment-name` to validate and export an existing checkpoint without starting another training run. Metrics are written inside that run's folder so experiments do not overwrite one another.

To use a different dataset, pass --data C:\path\to\sideline-soccer\data.yaml to the training script.

For a deployable model, collect video from the exact iPhone, mount position, pitch size, and shooting distance. Sample frames across multiple matches and lighting conditions; annotate ball, players, and referee. Split by entire match and camera position before training so near-duplicate frames do not appear in both train and validation. Inspect ball recall and false locks at the expected distance, then tune confidence and temporal tracking against held-out games.

## Included browser model

The repository includes `soccer-yolo11n-1280.onnx` (11,070,311 bytes). Its SHA-256 is `6A72DD73ECF6790ED4CE8C565835A418906CB08F09871BBF0A337647B9120BB6`. The browser page downloads this file from the repository on first use and stores it in Safari's local IndexedDB when available. Users can instead load a different ONNX model from iPhone Files. This download requires a working phone internet route; after the model is saved, the model bytes remain on the phone.

The export metadata identifies the upstream Ultralytics license as AGPL-3.0. The included model is distributed with the AGPL-3.0 text in `AGPL-3.0.txt`. The source Football Image Dataset is separately licensed CC BY 4.0; its attribution and license are documented above.

## Load the model in the iPhone page

For the bundled baseline, open the ESP32 page in Safari and tap **Download + load soccer model**. It downloads the ONNX file through the phone's internet connection and saves it on the phone when browser storage is available. To use a newly trained or different model, copy its `.onnx` file into iPhone Files, choose it under **Use a different soccer model**, and tap **Load chosen model**. In either case inference runs on the phone; the ESP32 receives only aim and motor commands.

The browser decoder expects the YOLO output for a 1280×1280 input with classes in this exact order: `ball`, `player`, `referee`. The current baseline uses confidence thresholds of 0.12 for balls and 0.18 for players/referees. The ball threshold was lowered from 0.26 after a browser/WebGPU calibration run on the separate 125-image public ball-only dataset described below. It requests the WebNN NPU device if the browser exposes it, then tries ONNX Runtime WebGPU with WASM fallback, then WASM CPU. The ESP32 page enables cross-origin isolation; when Safari provides `SharedArrayBuffer`, the WASM fallback uses up to four CPU threads, otherwise it uses one. This is a CPU optimization and does not access Apple's Neural Engine. The model fails ONNX Runtime Web's legacy WebGL provider on unsupported YOLO operators, so WebGL is not used. The generic MediaPipe COCO detector remains available as a fallback. The ONNX runtime downloads from jsDelivr on first use; the ESP32 page caches successful runtime and MediaPipe downloads in a same-origin service worker. The selected ONNX model is stored separately in IndexedDB. After a successful online load, both can be used without a network connection if Safari retains the site's data; iOS can evict site data.

## Baseline run and browser check

The 2026-10-11 YOLO11n run stopped after 40 epochs and exported a 10.6 MB ONNX model. On the 100-image broadcast validation split, aggregate validation was precision 0.747, recall 0.763, mAP50 0.763, and mAP50-95 0.496. A separate check loaded that ONNX file in ONNX Runtime WebGPU and ran the browser's 1280 preprocessing, 0.45 class-wise NMS, and box decoder against all 100 validation images. At IoU 0.50, using confidence thresholds of 0.26 for ball and 0.18 for players/referees, precision/recall was ball 0.485/0.590, player 0.948/0.983, referee 0.813/0.715. This is a runtime/decoder check on broadcast images, not a sideline test or a full mAP benchmark.

A second browser/WebGPU calibration used the 125 labeled test images from [martinjolif/football-ball-detection](https://huggingface.co/datasets/martinjolif/football-ball-detection), whose card describes a camera near midfield and declares CC BY 4.0. With 1280 preprocessing, class-wise NMS at 0.45, and IoU 0.50, ball confidence 0.26 yielded 53/125 recall (0.424) and 53/56 precision (0.946). At 0.12, it yielded 60/125 recall (0.480) and 60/65 precision (0.923). The app now uses 0.12 for balls while keeping 0.18 for players and referees. Since the threshold was selected on these same images, these numbers are calibration results rather than an untouched final test; the dataset is also broadcast-like, not an iPhone sideline view. Its training images were not used because the public repository did not contain matching YOLO label files.

The ONNX export metadata identifies the upstream Ultralytics license as AGPL-3.0. Its warm WebGPU inference took 66–106 ms on the local NVIDIA Pascal desktop; that timing does not predict iPhone performance. Measure the target phone's runtime and capture settings at the field.

The baseline's validation metrics come from broadcast frames, not the intended iPhone sideline viewpoint. Do not treat those scores as proof of sideline recall. Measure ball recall and false locks from held-out games recorded at the actual mount position before relying on automatic tracking.

A 25-epoch fine-tune from the baseline was checked on the same 100-image split and through the same browser/WebGPU decoder. At the then-current thresholds (0.26 ball, 0.18 player/referee) and IoU 0.50, ball precision/recall changed from 0.485/0.590 to 0.484/0.554; aggregate mAP50-95 changed from 0.496 to 0.492. The candidate improved some player scores but had more referee false positives. It is not bundled because it did not improve ball recall or overall mAP50-95. A sideline, match-separated dataset is still needed to finalize a model for the intended camera position.

A further five-epoch fine-tune used the 298 training images from [Football Game Object Detection Dataset](https://huggingface.co/datasets/martinjolif/football-player-detection), released under CC BY 4.0. Its `goalkeeper` and `player` labels were mapped to this model's `player` class. On the original 100-image validation split, this candidate reached mAP50 0.771 but mAP50-95 fell to 0.369. The browser/WebGPU decoder check at IoU 0.50 found ball precision/recall of 0.326/0.542 at confidence 0.12; the best ball F1 among tested thresholds was 0.519 at confidence 0.40 (precision 0.532, recall 0.506). The baseline at confidence 0.26 scored 0.485/0.590 (F1 0.532). Player precision/recall at 0.18 was 0.953/0.968; referee was 0.800/0.810. Exact image hashes and basenames showed no overlap between the supplemental training images and the original validation images, although video-level overlap cannot be ruled out. The public 125-image ball dataset is excluded from this candidate comparison because its source-video identifiers overlap the supplemental training set. This candidate is not bundled: its ball recall and localization quality did not beat the baseline, despite better referee recall and a slightly higher aggregate mAP50.

To check the viewpoint shift without a user-provided clip, I also used 237 sampled frames from the 46-second, 1280×720 CENTER-view recording `soccer_event_06/cam_01_S06` in [MUVY v1](https://zenodo.org/records/13883315). The sample contains 137 ball boxes and 441 `playing` (person) boxes. These are useful phone-recorded crowd-side scenes, but the archive's labels include low-confidence YOLO-World detections: only 3 of its 419 ball boxes in this recording have confidence at least 0.05. Treat these results as a noisy-label diagnostic, not a manually verified benchmark. With the same browser/WebGPU decoder at IoU 0.50, baseline ball precision/recall was 0.177/0.350 at confidence 0.12 and 0.310/0.255 at 0.18; the earlier player-dataset fine-tune candidate was 0.029/0.029 and 0.054/0.022 at those thresholds. The baseline was substantially better than that earlier candidate on this mobile-view sample. Keep the baseline as default and do not lower its threshold based on this noisy subset.

## Experimental handheld-view model

The page also offers `soccer-yolo11n-1280-mobile.onnx` as **Try phone-view model (experimental)**. It was fine-tuned for five epochs from the baseline using all 512 labeled broadcast training images plus 477 selected MUVY soccer frames from events 01–03, camera 01. MUVY player and goalkeeper labels map to `player`; balls and referees retain their classes. The model is 11,070,311 bytes with SHA-256 `3B4D52EF711E816D8D0039DDD5D879DA533D5840AD2143BAE4D761F500387DED`.

The MUVY source is Pessoa, Larissa; Alencar, Elton; Costa, Fernanda; Souza, Guilherme; and de Freitas, Rosiane, *Exploring multi-camera views from user-generated sports videos*, MUVY v1, Zenodo (2024), [DOI 10.5281/zenodo.13883315](https://doi.org/10.5281/zenodo.13883315). The Zenodo record declares CC BY 4.0; the fine-tuned model is an adaptation. The original baseline dataset remains credited above, and the resulting ONNX model retains the upstream AGPL-3.0 model licensing information.

On the 100-image broadcast validation split, the phone-view model reached mAP50 0.749 and mAP50-95 0.471, compared with the baseline's 0.763 and 0.496. Browser/WebGPU evaluation at IoU 0.50 showed ball precision/recall of 0.647/0.642 for the phone-view model at confidence 0.18 on the 237-frame MUVY event-06 sample, versus 0.310/0.255 for the baseline. On broadcast images at confidence 0.26, it scored 0.294/0.627 versus the baseline's 0.485/0.590. These are diagnostic scores against MUVY's generated annotations, not verified match results. The model is an optional phone-view experiment; the baseline remains the default. No held-out footage from the actual iPhone mount has been validated.

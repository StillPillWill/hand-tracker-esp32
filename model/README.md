# Soccer detector training

This folder defines a reproducible baseline training run. It does not claim that the model is ready for a full match: the source dataset contains broadcast-view frames, while the intended camera is a fixed iPhone on the sideline.

## Dataset

The baseline uses the [Football Image Dataset](https://github.com/skaczylo/Football-Image-Dataset), released under CC BY 4.0. It contains 612 1920×1080 frames: 512 train and 100 validation, with 500 labeled balls total (417 train, 83 validation), plus player and referee boxes. Credit the dataset author, skaczylo, and include the CC BY 4.0 license when redistributing adapted data or derived assets.

The dataset is downloaded and expanded under work/soccer-model, which is ignored by Git. It is not bundled in this repository. The upstream dataset's validation split is useful for checking that training runs, but it is too small and may not represent independent matches or the sideline viewpoint.

## Train a baseline

Python 3.10 or 3.11 and an NVIDIA GPU with CUDA are recommended. CPU training is supported but slow.

Run python -m pip install -r model/requirements.txt, then run python model/train_soccer.py from the repository root.

The script fine-tunes YOLO11n at 1280 pixels, evaluates the validation split, and exports a fixed-shape ONNX model. Outputs stay in work/soccer-model/training and are not committed automatically. Use `--name` to keep each experiment in its own run folder; `--weights` can point to a previous checkpoint. Use `--validate-only --weights path\to\best.pt --name experiment-name` to validate and export an existing checkpoint without starting another training run. Metrics are written inside that run's folder so experiments do not overwrite one another.

To use a different dataset, pass --data C:\path\to\sideline-soccer\data.yaml to the training script.

The training script also accepts a local YOLO dataset through `--data`. When a labeled field dataset is available, split it by whole match and camera position before training so near-duplicate frames do not cross between train and validation. The included phone-view model uses public held-out footage; no personal video is needed to install or run the application.

## Included browser model

The phone-view float model is `soccer-yolo11n-1280-mobile.onnx` (11,070,311 bytes; SHA-256 `3B4D52EF711E816D8D0039DDD5D879DA533D5840AD2143BAE4D761F500387DED`). The WASM-optimized phone-view model is `soccer-yolo11n-1280-mobile-int8.onnx` (3,655,881 bytes; SHA-256 `83448A2C84BE7A3A551718795D09EB1B2063EA539E99A993BBB89463D2E81B29`). WASM-only browsers download the quantized model; browsers with an ONNX Runtime Web accelerator use the float model. This avoids the quantized graph's slow WebGPU execution while shrinking the iPhone CPU download by 67%. The general soccer baseline remains available as `soccer-yolo11n-1280.onnx` (11,070,311 bytes; SHA-256 `6A72DD73ECF6790ED4CE8C565835A418906CB08F09871BBF0A337647B9120BB6`). The page downloads the selected file from the repository and stores it in Safari's local IndexedDB when available. Users can load a different ONNX model from iPhone Files. Model downloads require a working phone internet route; after saving, the model bytes remain on the phone.

The export metadata identifies the upstream Ultralytics license as AGPL-3.0. The included model is distributed with the AGPL-3.0 text in `AGPL-3.0.txt`. The source Football Image Dataset is separately licensed CC BY 4.0; its attribution and license are documented above.

## Load the model in the iPhone page

Open the ESP32 page in Safari and tap **Download + load phone-view model**. Tap **Load general soccer baseline** to switch to the broadcast-trained model. Either model downloads through the phone's internet connection and is saved on the phone when browser storage is available. To use another model, copy its `.onnx` file into iPhone Files, choose it under **Use a different soccer model**, and tap **Load chosen model**. In every case inference runs on the phone; the ESP32 receives only aim and motor commands.

The browser decoder expects 1280×1280 YOLO input with classes in this order: `ball`, `player`, `referee`. Both phone-view variants use confidence thresholds of 0.18 for all classes; the general baseline uses 0.12 for balls and 0.18 for players/referees. On its 237-frame held-out MUVY sample, the float phone-view model kept ball recall at 0.642 when the threshold increased from 0.12 to 0.18, while precision rose from 0.484 to 0.647. It requests WebNN/NPU or WebGPU only where ONNX Runtime Web supports the platform; the pinned 1.30.0 runtime uses multithreaded WebAssembly CPU on iOS. The ESP32 page enables cross-origin isolation; when Safari provides `SharedArrayBuffer`, the WASM path uses up to four CPU threads, otherwise it uses one. This is a CPU optimization and does not access Apple's Neural Engine. The generic MediaPipe COCO detector remains available as a fallback. The ONNX runtime downloads from jsDelivr on first use; the ESP32 page caches successful runtime and MediaPipe downloads in a same-origin service worker. The selected ONNX model is stored separately in IndexedDB. After a successful online load, both can be used without a network connection if Safari retains the site's data; iOS can evict site data.

## Baseline run and browser check

The 2026-10-11 YOLO11n run stopped after 40 epochs and exported a 10.6 MB ONNX model. On the 100-image broadcast validation split, aggregate validation was precision 0.747, recall 0.763, mAP50 0.763, and mAP50-95 0.496. A separate check loaded that ONNX file in ONNX Runtime WebGPU and ran the browser's 1280 preprocessing, 0.45 class-wise NMS, and box decoder against all 100 validation images. At IoU 0.50, using confidence thresholds of 0.26 for ball and 0.18 for players/referees, precision/recall was ball 0.485/0.590, player 0.948/0.983, referee 0.813/0.715. This is a runtime/decoder check on broadcast images, not a sideline test or a full mAP benchmark.

A second browser/WebGPU calibration used the 125 labeled test images from [martinjolif/football-ball-detection](https://huggingface.co/datasets/martinjolif/football-ball-detection), whose card describes a camera near midfield and declares CC BY 4.0. With 1280 preprocessing, class-wise NMS at 0.45, and IoU 0.50, ball confidence 0.26 yielded 53/125 recall (0.424) and 53/56 precision (0.946). At 0.12, it yielded 60/125 recall (0.480) and 60/65 precision (0.923). The general soccer baseline uses 0.12 for balls and 0.18 for players and referees. Since the threshold was selected on these same images, these numbers are calibration results rather than an untouched final test; the dataset is also broadcast-like, not an iPhone sideline view. Its training images were not used because the public repository did not contain matching YOLO label files.

The ONNX export metadata identifies the upstream Ultralytics license as AGPL-3.0. Its warm WebGPU inference took 66–106 ms on the local NVIDIA Pascal desktop; that timing does not predict iPhone performance. Measure the target phone's runtime and capture settings at the field.

The baseline's validation metrics come from broadcast frames, not the intended iPhone sideline viewpoint. Do not treat those scores as proof of sideline recall. Measure ball recall and false locks from held-out games recorded at the actual mount position before relying on automatic tracking.

A 25-epoch fine-tune from the baseline was checked on the same 100-image split and through the same browser/WebGPU decoder. At the then-current thresholds (0.26 ball, 0.18 player/referee) and IoU 0.50, ball precision/recall changed from 0.485/0.590 to 0.484/0.554; aggregate mAP50-95 changed from 0.496 to 0.492. The candidate improved some player scores but had more referee false positives. It is not bundled because it did not improve ball recall or overall mAP50-95. A sideline, match-separated dataset is still needed to finalize a model for the intended camera position.

A further five-epoch fine-tune used the 298 training images from [Football Game Object Detection Dataset](https://huggingface.co/datasets/martinjolif/football-player-detection), released under CC BY 4.0. Its `goalkeeper` and `player` labels were mapped to this model's `player` class. On the original 100-image validation split, this candidate reached mAP50 0.771 but mAP50-95 fell to 0.369. The browser/WebGPU decoder check at IoU 0.50 found ball precision/recall of 0.326/0.542 at confidence 0.12; the best ball F1 among tested thresholds was 0.519 at confidence 0.40 (precision 0.532, recall 0.506). The baseline at confidence 0.26 scored 0.485/0.590 (F1 0.532). Player precision/recall at 0.18 was 0.953/0.968; referee was 0.800/0.810. Exact image hashes and basenames showed no overlap between the supplemental training images and the original validation images, although video-level overlap cannot be ruled out. The public 125-image ball dataset is excluded from this candidate comparison because its source-video identifiers overlap the supplemental training set. This candidate is not bundled: its ball recall and localization quality did not beat the baseline, despite better referee recall and a slightly higher aggregate mAP50.

To check the viewpoint shift without a user-provided clip, I used 237 sampled frames from the 46-second, 1280×720 CENTER-view recording `soccer_event_06/cam_01_S06` in [MUVY v1](https://zenodo.org/records/13883315). The sample contains 137 ball boxes and 441 `playing` (person) boxes. These phone-recorded crowd-side scenes have machine-generated labels; only 3 of the recording's 419 ball labels carry confidence of at least 0.05 in the source annotation. Treat the results as a noisy-label diagnostic, not a manually verified benchmark. The general baseline scored ball precision/recall 0.177/0.350 at confidence 0.12 and 0.310/0.255 at 0.18; an earlier player-dataset fine-tune scored 0.029/0.029 and 0.054/0.022. The baseline remains available as a broadcast-oriented alternative.

## Default handheld-view model

The float phone-view model `soccer-yolo11n-1280-mobile.onnx` was fine-tuned for five epochs from the baseline using all 512 labeled broadcast training images plus 477 selected MUVY soccer frames from events 01–03, camera 01. MUVY player and goalkeeper labels map to `player`; balls and referees retain their classes. The model is 11,070,311 bytes with SHA-256 `3B4D52EF711E816D8D0039DDD5D879DA533D5840AD2143BAE4D761F500387DED`.

The MUVY source is Pessoa, Larissa; Alencar, Elton; Costa, Fernanda; Souza, Guilherme; and de Freitas, Rosiane, *Exploring multi-camera views from user-generated sports videos*, MUVY v1, Zenodo (2024), [DOI 10.5281/zenodo.13883315](https://doi.org/10.5281/zenodo.13883315). The Zenodo record declares CC BY 4.0; the fine-tuned model is an adaptation. The original baseline dataset remains credited above, and the resulting ONNX model retains the upstream AGPL-3.0 model licensing information.

On the 100-image broadcast validation split, the phone-view model reached mAP50 0.749 and mAP50-95 0.471, compared with the baseline's 0.763 and 0.496. On the same 237-frame MUVY event-06 sample, browser/WebGPU evaluation at IoU 0.50 showed ball precision/recall of 0.647/0.642 at confidence 0.18, versus 0.310/0.255 for the baseline. Player precision/recall at confidence 0.18 was 0.351/0.317 for the phone-view model and 0.170/0.252 for the baseline. At confidence 0.12, the phone-view model's ball precision was 0.484 with the same 0.642 recall, so the app uses 0.18 for phone-view balls to reduce false positives. On broadcast images at confidence 0.26, the phone-view model scored 0.294/0.627 versus the baseline's 0.485/0.590. The phone-view model is therefore the default for the intended amateur sideline use; the baseline remains available for broadcast-style footage. These are diagnostics against MUVY's generated annotations, not verified match results, and the exact iPhone mount has not been measured.

A wider browser/WebGPU diagnostic sampled 449 frames from seven additional MUVY streams: event 04 camera 03 and event 06 cameras 01–06. It contains 340 ball boxes and 1,793 mapped player boxes. At the app's default thresholds, ball precision/recall was 0.342/0.368 for the phone-view model at confidence 0.18 and 0.349/0.235 for the baseline at confidence 0.12. Player precision/recall at confidence 0.18 was 0.392/0.694 for the phone-view model and 0.319/0.633 for the baseline. Camera results vary substantially: on event 06 camera 01, the phone-view model reached ball precision/recall 0.789/0.625; on camera 04 it reached 0.719/0.697, while cameras 03 and 05 had no matched ball boxes. Several streams also have very sparse or incomplete machine-generated labels, and the sample contains no referee labels. Treat these as noisy-label diagnostics, not measured match accuracy or a guarantee for the intended iPhone mount.

## WASM-optimized phone model

The page selects `soccer-yolo11n-1280-mobile-int8.onnx` when ONNX Runtime Web will use WASM only. It uses per-channel signed int8 weights and uint8 activations in a QDQ graph. The quantizer calibrates on 48 evenly sampled MUVY training images from events 01–03/camera 01 and 12 regularly spaced broadcast training images; no held-out evaluation images are used. Recreate it with `python model/quantize_soccer.py` after preparing the documented training data and installing `model/requirements.txt`.

The float and quantized files were run through ONNX Runtime Web 1.30.0 WASM with four threads, the app's 1280 preprocessing, 0.45 class-wise NMS, and confidence 0.18 on the same 449 held-out MUVY frames. Against their generated labels at IoU 0.50, ball precision/recall was 0.342/0.368 for float and 0.368/0.371 for int8; player precision/recall was 0.392/0.694 for float and 0.406/0.688 for int8. On the local desktop browser, median inference time fell from 750 ms to 712 ms and the p95 from 816 ms to 746 ms. These latency figures do not predict iPhone performance. The QDQ model also ran on desktop WebGPU but was much slower there, so the app uses the float model whenever ONNX Runtime Web lists an accelerator provider. MUVY labels are machine-generated; the accuracy figures remain diagnostics, not manually verified field results.
